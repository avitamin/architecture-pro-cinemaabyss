# 009. Единая точка входа и общие функции API Gateway

Дата: 2026-11-06. Статус: принято; собственный proxy и путь замены готовым Gateway уточнены в ходе обсуждения, минимальный состав — в [ADR 010](010-minimal-container-topology.md).

Основание: пользователь определил API Gateway как центральную точку входа и выбрал мониторинг, логирование, кэширование, аутентификацию и авторизацию в числе его обязанностей.

## Контекст и ограничения

[Задание 1](../../../Project_template.md) требует единую точку вызова сервисов. Задание 2 предусматривает proxy/API Gateway для Strangler Fig с переключением трафика Movies по флагу. Это связывает целевую точку входа с постепенным выделением сервисов из монолита.

В задании 2 прямо указано: «Реализуйте сервис на любом языке программирования в ./src/microservices/proxy». Для выполнения задания эта формулировка трактуется как собственная реализация proxy с управляемой маршрутизацией. Задания 3–4 продолжают работу с его образом, CI/CD, Kubernetes и Helm; задание 5 требует Istio и Circuit Breaker для monolith и Movies. Замена требуемой реализации одной конфигурацией готового шлюза из условий не следует.

Kong в условиях заданий и исходной конфигурации репозитория не задан. Это готовая реализация Gateway, которая направляет запросы по настроенным маршрутам и применяет плагины; [документация Kong](https://developer.konghq.com/gateway/traffic-control/proxying/). После сравнения пользователь выбрал собственный proxy с возможностью позднее перейти на готовое решение, например Kong. Для минимального варианта в ADR 010 выбран Go; Kong остаётся альтернативой, а не обязательным компонентом.

В заданиях 2–5 нет требования реализовать регистрацию, вход конечных пользователей, выпуск токенов или внедрить отдельную систему идентификации. Упоминание аутентификации в инструкции развёртывания относится к registry. Принятые обязанности Gateway описывают To-Be архитектуру, а обязательный объём реализации учебного proxy ограничен условиями соответствующего задания. Выбор конкретного поставщика идентификации или протокола входа не должен становиться дополнительным условием выполнения задания 2.

В текущем [каталоге proxy](../../../src/microservices/proxy/) находится только `.gitkeep`. В проверенных обработчиках [монолита](../../../src/monolith/main.go) и [Movies](../../../src/microservices/movies/main.go) нет механизма аутентификации, в [OpenAPI](../../../api-specification.yaml) не описана схема безопасности. Поле `password_hash` в [SQL](../../../src/database/init.sql) само по себе не подтверждает реализацию входа пользователей. Gateway и выбранные общие функции предстоит реализовать.

## Альтернативы и выбор

| Подход | Польза | Цена и ограничение |
|---|---|---|
| Gateway только маршрутизирует запросы | Минимум логики на входе | Общие проверки и наблюдение за входящим трафиком приходится отдельно организовывать в сервисах |
| Gateway маршрутизирует и выполняет общие функции | Единые правила доступа и обработки клиентских запросов, общие логи и метрики на входе | Нужно ограничить ответственность Gateway, обеспечить его доступность и согласовать политики с сервисами |

Выбран второй подход, соответствующий [Gateway Offloading](https://learn.microsoft.com/en-us/azure/architecture/patterns/gateway-offloading). Внешние клиенты обращаются к доменным API через Gateway. Во время миграции он направляет запрос в монолит или выделенный сервис по правилам задания 2; целевые доменные операции выполняются сервисами-владельцами.

| Функция | Ответственность Gateway и её граница |
|---|---|
| Маршрутизация | Направлять запрос в нужный сервис; сохранять единую клиентскую точку входа при миграции |
| Мониторинг | Публиковать метрики входящих запросов, ошибок и задержек; сведения о работе фоновых обработчиков предоставляют сами участники |
| Логирование | Записывать структурированные сведения о запросах и передавать идентификатор корреляции; исключать токены, пароли и ненужные персональные данные |
| Кэширование | Повторно использовать только разрешённые политикой ответы чтения с учётом доступа, ключа кэша и актуальности |
| Аутентификация | Проверять подлинность представленного подтверждения личности по выбранному механизму и передавать проверяемый контекст пользователя |
| Авторизация | Проверять общие разрешения на маршрут и действие; доменные проверки конкретного объекта остаются у владельца данных |

Например, Gateway проверяет, что запрос к API подписок допускается для данного пользователя, а Subscriptions проверяет право пользователя на конкретную запрошенную подписку. Успешная проверка на входе не разрешает произвольный доступ к чужим данным. Доверие к переданному контексту и защита от обхода проверок должны быть обеспечены при реализации. Это разделение согласуется с [рекомендациями OWASP по проверкам на границе и в сервисах](https://cheatsheetseries.owasp.org/cheatsheets/Microservices_Security_Cheat_Sheet.html#edge-level-authorization).

Хранение учётных данных, вход пользователя и выпуск подтверждения личности требуют явного владельца ответственности в целевой архитектуре; наличие проверки в Gateway не определяет этого владельца и не требует отдельного микросервиса само по себе. Впоследствии в ADR 010 владельцем выбран Users, без отдельного IdP. Формат токенов или сессий не фиксируется; реализация полного входа пользователей не добавляется к обязательным требованиям учебного proxy.

Общие функции Gateway не меняют владение данными из [ADR 007](007-domain-data-and-purchase-saga.md) и хореографию из [ADR 008](008-purchase-saga-choreography.md). Gateway не читает чужие таблицы и не координирует шаги покупки. Асинхронные события идут между участниками через Kafka, поэтому HTTP-ответ на входе не подтверждает завершение саги.

Основание выбора — единообразная обработка клиентского трафика при сохранении бизнес-правил у доменных владельцев. Для учебной реализации выбран собственный proxy. Система сбора метрик и логов, хранилище кэша и число экземпляров этим решением не определяются; в минимальном варианте кэш выключен до появления измерений и политики актуальности.

## Последствия и риски

Кэш включается для явно разрешённых сценариев, а не для всех ответов по умолчанию. Неперсонализированные ответы каталога могут стать кандидатами после выбора политики. Защищённые ответы требуют проверки доступа и при попадании в кэш; персональные ответы не должны попадать в общий кэш без специально определённой изоляции. Нужно соблюдать директивы `Cache-Control`, включая `private` и `no-store`, и ограничения для запросов с `Authorization`. [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5).

Для готового рейтинга уже выбрана персистентная проекция в PostgreSQL Movies по [ADR 004](004-rating-read-projection.md). Кэш Gateway не заменяет эту проекцию. Кэширование карточки может задержать показ нового сохранённого рейтинга; его нельзя включать без согласованной политики обновления или инвалидации, сохраняющей выбранное поведение карточки. Состав кэшируемых ответов, TTL и допустимая дополнительная задержка пока не определены.

Единая точка входа — логическая роль, а не обязательный единственный экземпляр. Сбой Gateway может сделать недоступными клиентские операции даже при работающих доменных сервисах. Вероятность и нагрузка неизвестны; последствия затрагивают входящий трафик. При проектировании развёртывания нужно определить доступность и масштабирование Gateway. Они ещё не подтверждены конфигурацией или запуском.

Логи Gateway показывают входящий запрос и его HTTP-результат. Для пересчёта рейтинга и саги нужны также события и метрики доменных участников: отставание потребителей, неотправленный Outbox и незавершённые операции. Конкретный способ сбора и хранения наблюдений остаётся открытым; мониторинг только на входе не подтверждает работу всей цепочки.

## Проверка и пересмотр

После реализации проверить маршрутизацию и переключение Movies, общие проверки доступа и отказ в доступе к чужому объекту, связь запросов с логами и метриками. Для выбранных сценариев кэша проверить актуальность данных и отсутствие выдачи персонального ответа другому пользователю. Отдельно проверить работу при недоступности экземпляра Gateway и наблюдаемость асинхронной обработки.

`NOT RUN` — runtime-проверки: текущий этап описывает целевую архитектуру. Требования к реализации proxy/events в заданиях 2–5 этим ADR не переписываются; объём проверки их MVP определяется заданиями.

Пересмотреть распределение функций, если Gateway начнёт содержать доменные правила, мешать независимому развитию сервисов либо не выполнять согласованные требования к доступности и задержке. Политику кэша пересматривать при изменении персонализации, прав доступа или требований к актуальности.
