# 004. Персистентная модель чтения рейтинга в Movies

Дата: 2026-11-06. Статус: принято.

Основание: пользователь предложил публиковать готовый рейтинг через Kafka и после сравнения способов чтения подтвердил, что потребитель Movies обновляет значение в своём персистентном хранилище. Для него принят предложенный PostgreSQL, уже используемый в проекте.

## Контекст и ограничения

[ADR 003](003-rating-recalculation-events.md) определяет асинхронный пересчёт затронутых фильмов и показ последнего успешно рассчитанного значения. Теперь определены доставка готового результата каталогу и место его чтения.

В текущем [Movies](../../../src/microservices/movies/main.go) карточка читает `rating` из таблицы `movies`; [Compose](../../../docker-compose.yml) уже содержит PostgreSQL. Потребителя рассчитанных рейтингов в Movies пока нет. Существующая общая БД монолита и Movies описывает исходное состояние, а не выбранное физическое размещение целевых хранилищ.

## Альтернативы и выбор

| Подход | Польза | Цена и ограничение |
|---|---|---|
| Держать последние рейтинги в памяти потребителя и восстанавливать из Kafka | Чтение по идентификатору фильма без отдельного постоянного хранилища проекции | После запуска требуется восстановление состояния; готовность чтения зависит от завершения этого процесса и доступности журнала |
| Сохранять полученные рейтинги в PostgreSQL Movies | Результаты доступны после перезапуска приложения; карточка читает их привычным запросом к БД | Нужно поддерживать согласованность сохранённой проекции с поступающими обновлениями |

Выбрана персистентная модель чтения в PostgreSQL, логически принадлежащая Movies:

1. Обработчик рейтингов публикует готовое значение для конкретного фильма в Kafka.
2. Потребитель в Movies получает обновление и сохраняет значение для соответствующего фильма в своём хранилище.
3. API Movies читает сохранённый рейтинг вместе с данными карточки. Получение карточки не ожидает нового сообщения или пересчёта.

Личные оценки и правила расчёта остаются ответственностью Viewer Activity. Movies владеет копией готового результата для чтения. Такая копия — проекция исходных данных: она обновляется по сообщениям, а самостоятельно вычислять рейтинг каталогу не требуется.

Обоснование — сохранить разделение ответственности и обеспечить чтение уже готового рейтинга при остановке обработчика или недоступности Kafka, пока API и БД Movies доступны. Дополнительное хранилище вроде Redis для этого решения не требуется.

Выбор PostgreSQL определяет технологию и владельца модели чтения. Состав приложений, отдельные логические БД и допустимый общий физический экземпляр для учебного окружения впоследствии определены в [ADR 010](010-minimal-container-topology.md).

## Последствия и риски

Изменение личной оценки и обновление копии в Movies происходят асинхронно. Во время отставания карточка показывает последнее сохранённое значение; до первого результата рейтинга нет, как согласовано в ADR 003.

Потребителю потребуется корректно обрабатывать повторную доставку и не допускать замены более нового результата устаревшим. Ошибка в этом месте может вернуть старый рейтинг; вероятность без реализации неизвестна, последствия ограничены неверной актуальностью отображаемого значения. В ADR 010 выбраны монотонная версия результата для фильма, Outbox публикации и атомарное применение новой проекции с отметкой обработки; детали этих механизмов подлежат реализации и проверке.

Долгое хранение сообщений в Kafka само по себе не определяет восстановление проекции. Политику хранения топика результатов нужно выбрать явно; compaction по ключу фильма позволяет сохранять последнее значение для последующего восстановления. Это возможность Kafka, а не уже настроенная гарантия проекта: [документация Kafka 2.7](https://kafka.apache.org/27/design/design/#log-compaction).

## Проверка и пересмотр

Для будущей реализации проверить обновление только нужного фильма, чтение значения после перезапуска Movies, сохранение последнего результата при остановке обработчика и отсутствие рейтинга до первого сообщения. Проверить повторную доставку и защиту от устаревших обновлений по версии фильма.

`NOT RUN` — runtime-проверки: потребитель и целевой поток обновления ещё не реализованы; решение относится к архитектуре задания 1.

Пересмотреть хранилище модели чтения, если измеренная нагрузка или требования к задержке запросов покажут, что PostgreSQL не обеспечивает нужное поведение, либо изменятся требования к самостоятельности каталога и восстановлению данных.
