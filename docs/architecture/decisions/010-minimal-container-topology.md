# 010. Минимальный состав контейнеров To-Be

Дата: 2026-11-06. Статус: принято в рамках делегированного выбора оставшихся деталей задания 1.

Основание: после выбора границ доменов, потоков событий и Gateway пользователь поручил завершить задание, выбирая очевидные решения по принципу минимальной сложности. Собственный proxy и возможность последующей замены готовым Gateway согласованы отдельно.

## Контекст и результат

[Задание 1](../../../Project_template.md) требует домены, интеграции и единую точку вызова сервисов на контейнерной диаграмме C4. Результат — [диаграмма SVG](../diagrams/cinema-to-be-containers.svg) и [редактируемый исходник drawio](../diagrams/cinema-to-be-containers.drawio). Исходник открывается в diagrams.net; при изменении нужно обновлять и SVG.

В C4 контейнер — приложение или хранилище данных, а не обязательно Docker-контейнер. На схеме указаны типы, технологии, ответственность и подписанные однонаправленные связи. Стрелки обозначают инициатора обращения: потребитель обращается к Kafka для чтения. Направления бизнес-событий раскрыты в подписях и сценариях ниже. Основание нотации: [C4 Container diagram](https://c4model.com/diagrams/container), [C4 notation](https://c4model.com/diagrams/notation).

## Выбранный состав

| Домен / общая роль | Приложения | Владеет данными и правилами |
|---|---|---|
| Users | Users API | Учётные записи, профиль, учётные данные; ответственность за вход и подтверждение личности |
| Movies | Movies API с потребителем готовых рейтингов | Метаданные фильмов, жанры, персистентная проекция общего рейтинга |
| Payments | Payments API с обработчиками событий и Outbox relay | Денежные операции; состояние оплаты и полученный результат активации для этой покупки |
| Subscriptions | Subscriptions API с обработчиками событий и Outbox relay | Тариф, период и право доступа; применение подтверждённой оплаты |
| Viewer Activity | Viewer Activity API и отдельный Rating Worker | Просмотры, личные оценки, отзывы, вычисление общего рейтинга |
| API Gateway | Собственный proxy | Маршрутизация и общие функции входящего HTTP-трафика по [ADR 009](009-api-gateway-responsibilities.md) |
| Event Streaming | Apache Kafka | Передача и хранение событий; бизнес-состояние остаётся у доменных владельцев |

Для API, proxy и воркера выбран Go: [монолит](../../../src/monolith/go.mod) и [Movies](../../../src/microservices/movies/go.mod) уже используют этот стек. Это осознанное сокращение числа технологий, а не ограничение задания. Версии зависимостей новых сервисов определяются при реализации.

Каждый домен получает свою логическую PostgreSQL БД и доступ только к ней. В учебном окружении допускается один физический экземпляр PostgreSQL с отдельными БД и пользователями. Общий экземпляр экономит инфраструктуру, но разделяет ресурсы и отказ между доменами; отдельные экземпляры понадобятся при требованиях к независимой доступности или нагрузке. Междоменные SQL-запросы, запись в чужие таблицы и внешние ключи между доменами не используются. Идентификаторы других доменов передаются как ссылки через контракты.

Viewer Activity API и Rating Worker принадлежат одному домену и работают с одной доменной БД. Воркер вынесен в отдельное приложение, чтобы расчёт не занимал обработчики HTTP и мог масштабироваться независимо. Отдельный домен Ratings и дополнительное хранилище ему не нужны: правила вычисления опираются на личные оценки Viewer Activity.

Consumers и Outbox relay показаны как внутренние роли сервисов. Отдельный процесс для каждого такого обработчика пока не обоснован. В отличие от них, отдельный процесс расчёта рейтинга выбран явно.

## Взаимодействие

Клиент обращается к Gateway по HTTPS/JSON. Gateway маршрутизирует запросы к пяти доменным API по HTTP/JSON; каждый API проверяет права на свои ресурсы и работает со своей БД. Защита внутренних соединений и запрет обхода Gateway определяются при развёртывании. Gateway не получает доступа к доменным БД.

Покупка: **Payments → Kafka → Subscriptions → Kafka → Payments**. Подтверждённая оплата запускает активацию, Subscriptions публикует результат, Payments сохраняет его рядом с состоянием покупки. Это наблюдение за результатом своего платежа, а не отдельный оркестратор. Применяются хореография из [ADR 008](008-purchase-saga-choreography.md), локальные транзакции, Outbox и идемпотентная обработка из [ADR 006](006-payment-transactional-outbox.md). Пока результат не получен, покупка остаётся в промежуточном состоянии; HTTP-успех или отправка события не означают активацию доступа.

Рейтинг: **Viewer Activity API → Kafka → Rating Worker → Kafka → Movies**. API сохраняет оценку и исходящее событие одной локальной транзакцией. Воркер читает оценки только затронутого фильма из БД Viewer Activity, сохраняет результат и событие публикации через Outbox. Для первого варианта достаточно среднего арифметического текущих личных оценок; при отсутствии оценок результат отсутствует. Это не рекомендации и не рейтинг, задаваемый редактором каталога.

У результата есть монотонная версия для фильма, связанная со снимком исходных оценок. Конкурирующие расчёты одного фильма согласуются внутри Viewer Activity. Movies атомарно применяет только более новую версию вместе с отметкой обработки. Повторы не создают повторного бизнес-эффекта, запоздалый результат не заменяет новый. Во время задержки или сбоя карточка показывает последнее сохранённое значение; до первого результата рейтинга нет. Если оценки закончились, новое версионированное событие явно очищает проекцию. Kafka не используется как хранилище для HTTP-чтения карточки. Основа потока: [ADR 003](003-rating-recalculation-events.md), [ADR 004](004-rating-read-projection.md).

Outbox не устраняет задержку и не обеспечивает доставку за пределами настроенного срока хранения Kafka. При реализации нужны идемпотентность, повторы, контроль отставания и восстановление проекций. Числовые пределы задержек, retention, схемы событий, правила компенсаций покупки и восстановление после длительного сбоя уточняются до запуска соответствующих сценариев; они не меняют выбранный состав контейнеров. Event Sourcing не вводится.

## Минимальность, альтернативы и развитие

| Выбор | Почему достаточен сейчас | Когда пересмотреть |
|---|---|---|
| Один API на домен; отдельный воркер рейтинга | Границы соответствуют данным и бизнес-правилам, расчёт отделён от HTTP | Если отдельная часть требует независимого жизненного цикла или масштабирования |
| Users владеет идентификацией | Не нужен ещё один домен или инфраструктурный продукт только ради диаграммы | При SSO, внешних пользователях или требовании готового IdP; формат токенов пока не фиксируется |
| Собственный Go proxy | Выполняет условие задания 2 и позволяет изучить переключение трафика | При росте эксплуатационных требований сравнить стоимость поддержки с Kong |
| Без отдельного Redis; кэш Gateway изначально выключен | Movies уже хранит готовую модель чтения; нет измеренной потребности в дополнительном кэше | После измерений и выбора правил актуальности и изоляции персональных ответов |
| PostgreSQL с логическим разделением | Уже есть в проекте, достаточно для выбранных данных | При измеренной потребности в иной модели хранения или физической изоляции |

Kong остаётся готовой альтернативой реализации Gateway. Для замены нужно сохранить клиентский API и проверить маршруты, заголовки, обработку ошибок, доступ и кэширование. Концептуальное сходство не гарантирует совместимость конфигурации. В своём proxy достаточно маршрутов и обычных middleware; собственную платформу плагинов не создаём. [Устройство проксирования Kong](https://developer.konghq.com/gateway/traffic-control/proxying/).

Istio умеет направлять трафик по заголовкам и распределять его между версиями по весам; это позволяет делать постепенное переключение. Такие правила не заменяют универсальные флаги бизнес-функций внутри приложения. В задании 2 переключением владеет собственный proxy и его флаг. Задание 5 добавляет Istio и Circuit Breaker. Если позже процентное распределение передаётся Istio, аналогичное распределение в proxy для того же маршрута отключается: у решения о доле трафика должен быть один владелец. [Traffic management Istio](https://istio.io/latest/docs/concepts/traffic-management/), [Traffic shifting](https://istio.io/latest/docs/tasks/traffic-management/traffic-shifting/).

Диаграмма описывает конечную To-Be архитектуру. Монолит и учебный сервис events остаются частью перехода по заданиям 2–5. MVP events публикует и читает сообщения с записью в лог; он не становится общим владельцем бизнес-правил всех доменов. Подробности Kubernetes, Helm, mesh, число реплик и отказоустойчивость относятся к развёртыванию и не изображаются дополнительными доменами.

## Проверка и граница результата

Задание 1 завершается архитектурными артефактами: диаграмма соответствует ADR, содержит пять доменов, единую точку входа, технологии, владельцев хранилищ и подписанные интеграции. SVG и drawio проверяются как XML, сопоставляются по узлам и связям; SVG проверяется после рендеринга. Ссылки в шаблоне должны вести на оба файла.

`NOT RUN` — реализация и runtime-проверки. В исходной системе остаются общая БД, независимые операции платежа и подписки, вручную заданный `movies.rating`; нет описанных Outbox и расчёта рейтинга. Текущий OpenAPI требует числовой рейтинг: отсутствие результата нужно отразить при последующей доработке контракта. Полная идентификация, разделение БД и оба бизнес-потока не выдаются за уже реализованные требования заданий 2–5.
