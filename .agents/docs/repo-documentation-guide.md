# Руководство по документации CinemaAbyss

Этот документ задаёт контекст для навыка `project-docs`. Инструкции и вспомогательный контекст работы агента находятся в `.agents/`, точка входа — [AGENTS.md](../../AGENTS.md). Архитектурная документация проекта размещается в `docs/architecture/`: решения — в `decisions/`, диаграммы — в `diagrams/`. Правила совместной работы описаны в [architecture-workflow.md](../architecture-workflow.md).

## Источники и разрешение расхождений

Разделяй намерение, требования, контракт, реализацию и наблюдение:

| Вопрос | Основной источник | Граница доказательства |
|---|---|---|
| Что делать сейчас и какие решения приняты | Последний явный запрос пользователя и согласованные решения | Предложение агента, молчание и дата файла не означают согласия |
| Что требуется сдать | [Project_template.md](../../Project_template.md), задания 1–5 | Это требования и примеры выполнения, а не отчёт о готовности |
| Какой API заявлен | [api-specification.yaml](../../api-specification.yaml) | Контракт нужно сопоставлять с реализацией и проверками |
| Что реализовано | Исходники, SQL, конфигурация и тестовые сценарии текущей рабочей копии | Наличие исходников не доказывает работоспособность запущенной системы |
| Что произошло при проверке | Фактический результат команды в указанной среде и на указанной ревизии | Доказательство действует только для проверенного сценария и среды |
| Где искать контекст | [README.md](../../README.md), [состояние проекта](../project-state.md), профильные README | Сводки могут отставать от исходников и требований |

Явное указание пользователя определяет текущий охват. Если оно меняет обязательный результат задания, назови это изменение и его последствия для сдачи. Не сокращай требования самостоятельно под предлогом MVP.

При расхождении API, теста и реализации покажи конкретные места и влияние на текущую задачу. Код описывает текущее поведение, но не отменяет контракт. Разрешай расхождение по явному требованию или уже согласованному решению; если оснований недостаточно, вынеси существенный выбор пользователю. Продолжай независимую часть работы.

До создания нового документа проверь существующего владельца темы. Ссылайся на него вместо копирования правил. Шаблон ADR находится в `architecture-workflow.md`; каталог `docs/architecture/decisions/` и записи создаются только при появлении решений. В `AGENTS.md` сохраняй короткие обязательные ориентиры и ссылки. Изменяемые сведения о прогрессе не переноси туда. В `project-state.md` добавляй ссылки на принятые ADR и результаты этапа; в шаблон задания — краткое обоснование решений и ссылки на соответствующие ADR и сдаваемые артефакты. Не добавляй пустые индексы и документы «на будущее».

## Стиль и границы содержания

- Пиши по-русски; сохраняй исходное написание команд, путей, API и идентификаторов. Новые имена файлов — ASCII.
- Отмечай факт, предположение, предложение и принятое решение так, чтобы их нельзя было перепутать. Для существенного факта давай ссылку на конкретный источник.
- Документируй ровно тот уровень подробностей, который нужен следующему действию. Обзор не обязан содержать полный план реализации.
- Существующие навыки указывай по именам из каталога среды. Не копируй их в репозиторий и не привязывай инструкции к личным абсолютным путям.
- Личный профиль знаний, секреты и содержимое локальных файлов аутентификации в документацию не переноси. Для конфигурации показывай безопасные заполнители.

## Проверки по типу изменения

| Изменение | Достаточная проверка |
|---|---|
| Инструкции и руководства | Соответствие согласованному процессу, отсутствие конфликтующих запретов, корректность ссылок, Markdown и diff |
| Состояние проекта | Адресная сверка каждого изменённого утверждения с источником; дата и граница выполненных проверок |
| ADR | Основание выбора, альтернативы, последствия, принимаемые риски, способ проверки и условие пересмотра |
| Описание API или данных | Сверка затронутого контракта, обработчика, схемы и сценариев тестов; запуск нужен, если заявляется проверенное поведение |
| Инструкция развёртывания | Сверка команд с конфигурацией; отдельно отметить статическую проверку, сборку и реально выполненное развёртывание |
| Отчёт о выполнении задания | Сопоставление с требованиями и фактическими результатами, включая запрошенные скриншоты |

Проверяй только затронутые утверждения и их зависимости. Документационная правка сама по себе не требует запуска сервисов, установки зависимостей или полного набора тестов. Если запуск не выполнялся, обозначь это, а не делай вывод о работоспособности.

Для каждого существенного результата используй статус и укажи уровень проверки:

- `PASS` — указанная проверка выполнена и прошла.
- `FAIL` — выполнена и выявила несоответствие.
- `NOT RUN` — не выполнялась; кратко укажи причину.
- `BLOCKED` — необходимая проверка недоступна из-за конкретного препятствия; это не означает блокировку всего проекта.

Минимальная запись результата: что проверяли, дата, ревизия или состояние рабочей копии, команда либо способ проверки, результат и ограничение. Успешная проверка HTTP API не подтверждает чтение сообщения из Kafka; сборка не подтверждает развёртывание. Проверка текста инструкций не доказывает, что агент будет следовать им в каждой будущей сессии.

## Завершение документационной задачи

1. Проверь локальные ссылки, структуру Markdown и отсутствие неподтверждённых утверждений.
2. Выполни `git diff --check`. Новые неотслеживаемые файлы проверь отдельно: обычный diff их не включает.
3. При изменении repo guide запусти `scripts/check_repo_guide.py` из каталога соответствующего установленного навыка, передав `docs/repo-documentation-guide.md` или `docs/repo-commit-guide.md`. Каталог навыка возьми из каталога среды. Скрипт проверяет обнаружение непустого файла, а не качество его содержания.
4. Обнови нужные ссылки и сводку состояния. Сообщи о результате и существенных ограничениях; не создавай отдельный отчётный файл без запроса.
