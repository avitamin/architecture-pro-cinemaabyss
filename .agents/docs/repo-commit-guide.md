# Руководство по коммитам CinemaAbyss

Этот документ задаёт проектный контекст для навыка `prepare-repo-commit`. Источники и уровень проверок описаны в [руководстве по документации](repo-documentation-guide.md).

## Приоритет источников

1. Явный запрос пользователя определяет действие: подготовить текст, создать коммит или опубликовать изменения. Уже данное разрешение в текущем запросе повторно не запрашивай.
2. Согласованные правила этого руководства и применимые инструкции пользователя задают процесс.
3. Текущие status и diff определяют фактический состав изменений; staged diff — содержимое будущего коммита.
4. История помогает понять стиль, но единичный коммит не устанавливает обязательную конвенцию.

Подготовка документации сама по себе не разрешает commit, push или публикацию PR. Выполняй их, когда пользователь явно включил соответствующее действие в запрос. Запрос локального коммита не включает push.

## Формат сообщения

Факт на момент подготовки руководства: история состоит из `51240c1 Initial commit`; документированной конвенции не было.

Согласованный формат: краткий английский заголовок с глаголом действия, конкретным объектом и без точки в конце. Например:

```text
Add architecture learning guidance
Document the current project state
```

Сообщение описывает фактический diff. Тело добавляй, если нужно объяснить причину или проверки. Не вводи обязательный Conventional Commits.

Перед коммитом или публикацией проверь подготовленный текст: без автоматической атрибуции ИИ, подписей агентов, названий моделей и ссылок на сессии. Сохраняй реальное авторство людей и необходимые технические упоминания, когда инструмент — предмет изменения. Проверки описывай по фактическому способу выполнения.

## Идентификаторы задач

Обязательного issue key нет. Не придумывай Jira-ключи по номерам учебных заданий. Добавляй идентификатор, только если пользователь задал его для текущей работы.

Проектное исключение для `prepare-repo-commit`: issue-key gate и `.agents/git-commit-gate.json` здесь не требуются. Универсальная проверка соответствия ключа задачи в ветке и сообщении к согласованному процессу без обязательных ключей не применяется; отсутствие её конфигурации не блокирует коммит. Остальные проверки состава изменений и сообщений сохраняются.

## Ветки

Факт исходной рабочей копии: ветка `main`, remote `origin` указывает на GitHub. Это не свидетельство настроек защиты удалённых веток.

Правило по умолчанию для этого небольшого учебного репозитория: работай в текущей именованной ветке; прямой локальный коммит в `main` допустим по явному запросу коммита. Не создавай ветку только ради пакета документации. Если пользователь просит отдельную ветку, используй короткое имя по задаче, например `docs/learning-workflow` или `feature/strangler-proxy`, без имени агента или модели.

При detached HEAD или конфликте с явно запрошенной веткой уточни только этот вопрос. Не используй stash, reset, принудительное переключение или удаление файлов для обхода чужих изменений.

## Состав коммита

1. Посмотри `git status --short`, текущую ветку и diff относящихся к задаче изменений, включая новые файлы.
2. Отдели изменения текущей задачи от прочих. Для первого документационного пакета состав ограничен пятью файлами, перечисленными в [состоянии проекта](../project-state.md).
3. Проверь выбранные файлы и добавляй их в staging явными путями только в рамках запроса, включающего staging или коммит. Не используй `git add .` для неоднородной рабочей копии.
4. Перед коммитом проверь `git diff --cached --stat`, `git diff --cached` и `git diff --cached --check`; сообщение должно соответствовать staged diff.
5. При посторонних staged-изменениях не включай и не убирай их молча. Назови конфликт состава и уточни границу коммита; независимую проверку своих файлов можно продолжить.
6. После коммита проверь результат и статус, сообщи хеш и оставшиеся относящиеся к задаче изменения.

## Проверки

Для документации достаточно проверок из [repo-documentation-guide.md](repo-documentation-guide.md): источники, ссылки, Markdown, затронутые сценарии инструкций и отсутствие ошибок whitespace. При изменении руководства проверь его обнаружение штатным `scripts/check_repo_guide.py` из каталога соответствующего навыка.

До staging обычный `git diff --check` не охватывает новые файлы. Для каждого такого файла можно выполнить `git diff --no-index --check /dev/null <path>` и проверить диагностику. Это не требует изменения индекса.

При изменениях кода, контрактов или конфигурации выбирай проверки по затронутому поведению и требованиям задания. Полный runtime-набор не является обязательным условием документационного коммита. `NOT RUN` у несвязанных runtime-проверок не блокирует такой коммит; не представляй их как успешные.

## Основания и настройки по умолчанию

Формат сообщения и отсутствие обязательных issue keys согласованы пользователем при подготовке проекта. Работа в текущей ветке — локальное правило по умолчанию, а не вывод о политике GitHub. Формальных требований к PR, релизам и защите веток сейчас нет в документах репозитория; их не нужно придумывать для локального коммита. При новом явном соглашении обновляй это руководство.
