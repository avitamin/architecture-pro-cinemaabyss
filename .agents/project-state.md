# Состояние CinemaAbyss

Дата сверки: 2026-11-07. Рабочая ветка — `cinema`; исходная реализация — `51240c1` (`Initial commit`). При продолжении сверяй текущую ревизию и затронутые файлы, а не считай эту запись автоматически актуальной.

## Текущий этап

**Задание 1 завершено на уровне проектирования.** В [Project_template.md](../Project_template.md) записаны решения и ссылки на [контейнерную диаграмму C4 в SVG](../docs/architecture/diagrams/cinema-to-be-containers.svg) и [редактируемый исходник drawio](../docs/architecture/diagrams/cinema-to-be-containers.drawio). Оба файла относятся к конечной To-Be архитектуре; реализация следующих заданий ещё не начата.

- [ADR 006 — надёжная публикация событий оплаты через Transactional Outbox](../docs/architecture/decisions/006-payment-transactional-outbox.md).

Пользователь делегировал оставшиеся очевидные детали по принципу минимальной сложности. Выбраны пять доменов: Users, Movies, Payments, Subscriptions и Viewer Activity; по одному API на Go, отдельный Rating Worker внутри Viewer Activity, логическая PostgreSQL БД каждого домена. В учебном окружении допустим общий физический PostgreSQL с отдельными БД и доступами. API и воркер Viewer Activity разделяют данные своего домена. Users владеет идентификацией; отдельный IdP не добавлен. Кэш Gateway изначально выключен; Redis не вводится.

Сохраняются согласованные потоки: пересчёт затронутых фильмов через Kafka с персистентной проекцией в Movies; последний рейтинг показывается во время задержки, до первого результата его нет. Начальная формула — среднее текущих личных оценок. Outbox, идемпотентность и версии результатов определены как требования к реализации. Для покупки выбрана хореография Payments → Kafka → Subscriptions → Kafka → Payments; Payments хранит состояние оплаты и полученный результат активации. Оркестратора и Event Sourcing нет.

API Gateway — собственный proxy на Go. Проверки конкретных ресурсов остаются в доменных сервисах. Kong сохранён как готовая альтернатива при проверке совместимости контрактов. Istio умеет маршрутизировать по заголовкам и весам; это не универсальные флаги бизнес-функций. Долей трафика в задании 2 управляет proxy. При последующей передаче этой функции Istio её отключают в proxy для того же маршрута.

По запросу пользователя история делится на два локальных коммита относительно исходного `origin/main`: подготовка репозитория и задание 1. Уточнения структуры документации относятся к первому коммиту; текущий ответ, ADR, диаграмма и этот снимок состояния — ко второму. Коммиты оформляются после завершения и проверки задания 1. Push и PR не выполнялись; PR из `cinema` в основную ветку предусмотрен после всех пяти заданий.

Архитектурные решения находятся в `docs/architecture/decisions/`, диаграммы — в `docs/architecture/diagrams/`. В `.agents/` остаются инструкции и вспомогательный контекст. Существенные новые решения обсуждаются по одному, пока пользователь не делегировал выбор; принятые ADR повторного согласования не требуют. Комитет — только по явному запросу пользователя. Две недели не являются установленным сроком проекта.

## Следующий шаг и детали реализации

Следующее учебное задание — 2: собственный proxy в `src/microservices/proxy`, флаг `GRADUAL_MIGRATION` и процент `MOVIES_MIGRATION_PERCENT`, затем требуемый events с API User/Payment/Movie, producer, consumer и записью в лог. Реализация ещё не начата. Сборка, CI/CD, Kubernetes, Helm и Istio Circuit Breaker относятся к заданиям 3–5.

Регистрация, вход и выпуск токенов не требуются заданиями 2–5. Расширение proxy авторизацией обсуждалось как возможность; оно не добавлено к обязательному MVP. Users — логический владелец идентификации в To-Be, формат токенов и протокол входа пока не выбраны. Принятые функции Gateway не означают их наличие в исходном коде.

До реализации целевых бизнес-потоков нужно детализировать контракты событий и покупки, компенсации, восстановление незавершённых операций и проекций, retention, числовые пределы задержки, метрики отставания и требования к доступности. `PaymentEvent` пока не связывает платёж с конкретной покупкой подписки; `Movie.rating` в текущем OpenAPI обязателен и числовой, поэтому отсутствие результата потребует изменения контракта. Эти ограничения не блокируют завершённую контейнерную диаграмму, но не позволяют заявлять работающую сагу или расчёт рейтинга.

Монолит и учебный events — переходные компоненты. MVP events с логированием не заменяет доменных участников To-Be и не подтверждает оплату. Решения по доменам, данным, Gateway, рейтингу и хореографии повторно не открывать без новых фактов.
